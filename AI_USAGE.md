# AI Usage Log

**Tools:** Claude Code, used through a structured process rather than ad hoc prompting: a written design spec, then a task-by-task implementation plan, then one implementation agent per task. Every task's diff was then read by a second, independent review agent that saw only the diff (not the implementation agent's reasoning), and fix rounds continued until that review came back clean. 35 commits on `feat/flowboard` (33 feature/fix, 2 setup), 141 tests across 18 suites.

This log is about where that process actually caught things, not a generic "AI accelerated development" summary.

## Where AI helped

- Turned a rough idea (a ClickUp/Asana-style hierarchy with permissions) into a written spec, then a dependency-ordered task plan, before any implementation code existed.
- Generated the RTK slices, async thunks, selectors, and the pure permission/validation/ordering libraries from that spec.
- Generated the Jest/RTL test suites alongside each implementation task.
- Generated the Tailwind component markup for the shell, sidebar, board, list view, and task drawer.
- Ran the independent review pass per task — reading only the diff is what surfaced the issues below; an agent reviewing its own implementation inline would have shared its own blind spots.

## Where it was wrong, and how that was caught

**An optimistic-update bug that neither file showed alone.** `moveTaskWithRollback` (`src/store/thunks/optimistic.ts`) applies its patch to the store synchronously, before dispatching the `moveTask` thunk, so that the drag visually completes before the network round-trip resolves. The bug: the thunk's own `getState()` call then observed the *already-moved* task — `task.primaryListId` was the destination list, not the source. Reading `optimistic.ts` alone looked fine (snapshot → patch → dispatch → rollback-on-reject); reading `taskThunks.ts` alone looked fine (check source list permission, check dest list permission, remap subtask statuses on cross-list moves). Only the combination was broken: the "source list" the thunk computed was always equal to the destination, which silently turned off both the cross-list subtask-status-remap branch (`toListId !== sourceListId` was always false) and the source-list permission check — a member could drag a task out of a list they could not even view, because the thunk never actually looked at the real source list to deny it. Fixed by threading an explicit `fromListId`, captured from the pre-patch snapshot, through to the thunk (see the doc comment on `moveTask` in `src/store/thunks/taskThunks.ts`, which spells out why this can't be reconstructed from `getState()` after the fact). Commit: `1f81fe4`.

**A drag-destination off-by-one on the board.** The first version of the board's drop-position math filtered the dragged card out of the destination column before computing `overIndex`, then looked up neighbours at that index. That's correct for upward drags but wrong for downward ones: every card after the dragged card's original position shifts down by one index once it's filtered out, so the computed neighbour pair was shifted and every downward within-column drop landed one slot higher than where it was dropped. A pick-up-and-immediate-put-back (no visible move) would silently relocate the card by one slot. Fixed by computing against the **unfiltered** column array and running it through dnd-kit's own `arrayMove` to get the post-drop order, then reading neighbours from that — mirroring the sidebar's existing `computeReorderPosition`. The math was also extracted into a pure function (`computeBoardDrop` in `src/components/board/boardDrop.ts`) with its own direct unit tests rather than only being exercised indirectly through component drag simulation. Commit: `dcf14ca`.

**An accessibility defect that only showed up as a flaky test.** Two tests passed or failed depending on suite run order. Digging in: Headless UI's `Dialog` (the task drawer) marks the rest of the app tree `inert` while open via `useInertOthers`. Any toast raised while the drawer was open was therefore unannounced to assistive tech and unclickable/untabbable — the flakiness was two tests racing on whether a toast from a prior test's drawer state was still inert when the next test queried it. The first fix attempt moved the toast into Headless UI's own `<Portal>`, which turned out not to help: `useInertOthers`'s "allowed" branch walks up from the dialog's own portal and inerts every *other* child of that same portal root, so a toast there is just as inert. The working fix (`src/components/ui/Toasts.tsx`) mounts the toast layer as its own direct child of `<body>`, outside both the main app tree and Headless UI's portal root — `useRootContainers` treats any such body child as a legitimate, non-inert container. Toasts still announce via `role="alert"` and auto-dismiss after four seconds; the one limitation the fix doesn't solve, and the README documents, is that a keyboard-only user still can't `Tab` into the toast layer to dismiss it early, since it sits outside the dialog's own focus trap. Commit: `1d4a2ed`.

**A reviewer disproved a planning instruction that was simply wrong.** An earlier doc comment on the sidebar's reorder helper (`computeReorderPosition`) claimed that reading neighbour positions via `arrayMove`'s post-drop order was "correct... unlike naively reusing `overIndex` as the insertion index into the array with the active node removed, which only works when dragging upward" — implying the filtered-array approach was actually broken for downward drags in that function specifically. Exhaustive comparison across every index pair showed the two constructions produce identical neighbour positions *in that function*, because `nodes` there is always the unfiltered pre-drag array to begin with — the claim conflated this function with the genuinely broken board case above. The comment was corrected to say plainly that going through `arrayMove` is a clarity choice, not a correctness fix, for this particular function, while still flagging precisely why the *board's* original version (which did filter first) was the real bug. Commit: `c5f7259`.

**Repeated weak assertions.** Several tests in early drafts asserted conditions that the named bug would also have satisfied — e.g. checking that a task's list changed without checking the task's *position*, which wouldn't have caught the off-by-one above — and at least one test's title described a behavior its body never actually exercised. Each was caught in the diff-only review pass (which reads test intent against test body, not against the author's stated intent) and rewritten to assert the specific, falsifiable thing the bug would get wrong.

## What a human decided

- The permission precedence itself: archived-checked-first (even before admin bypass), deny-always-wins, private-needs-an-allow-anywhere-in-chain, pass-through-as-navigation-not-visibility. This shape came from the written spec, not from the implementation agent improvising it, and the review pass's job on every permissions-adjacent task was to check the code against that exact ordering.
- Scope boundaries that AI would otherwise have been happy to expand: container CRUD stays admin-only rather than growing a role system; optimistic updates apply to drag-and-drop only, not to every async write; status sets are seed-defined, not UI-editable. Each is a deliberate one-pattern-per-concern decision, written up as a trade-off in `README.md` rather than left implicit.
- The choice of Jest over Vitest in a Vite project, and `@swc/jest` to keep it fast — a deliberate exercise in working against the "obvious" tool choice.
- Accepting the toast/focus-trap limitation as documented, shippable behavior (with `role="alert"` and auto-dismiss as the mitigation) rather than building a full custom focus-trap override to chase 100% keyboard reachability for a take-home.
